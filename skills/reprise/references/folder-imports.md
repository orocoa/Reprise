# Ordered folder and ZIP-content import

Start with `import-folders --manifest FILE --check` when the user asks to inspect scope or cost. This reads only filesystem metadata and ZIP directories, creates no versions or recovery copies, and reports expanded logical sizes, an unknown-sharing range, retained-readback expansion, a capacity planning budget and per-volume scope. It does not establish recovery or removal safety. `capacity_available` compares current free space with the planning budget, not a guarantee of sufficient future physical space. No user content is deleted to make room.

`import-folders --manifest FILE --preflight FINGERPRINT` performs the reviewed import. The fingerprint binds input order, titles, paths, metadata and the data directory. Inputs and capacity are checked again before saving, including queue-time changes. The CLI can also explicitly start an import without the optional fingerprint; it still performs the cost/capacity gate. In the web UI, review the preview before choosing to save.

Source-body scanning cannot establish a new baseline after confirmation: the accepted preview is checked again after scanning, and each snapshot publication checks its expected source state and remaining capacity budget. Nested cross-device mount points in inputs or managed data are unsupported; manage those volumes separately. Different input-root volumes remain distinct, and incompatible costs never produce a combined reclaim figure.

Import saves explicitly ordered inputs into one folder project, materializes every saved version into a retained recovery directory, reads it back, checks originals again, and produces a report. The last input must be the working folder to keep. Inputs must not overlap each other or Reprise data. Existing folder projects require an explicit `project_id`; this appends recording events without rewriting prior commits. Imported Git sources remain read-only.

Each version retains its original path, input position and exact snapshot SHA. The import time and parent edges record this import, not original development chronology. Ordinary folders preserve the existing snapshot metadata scope. An excluded `.git`, tracked source, hard links, unsupported metadata, changed original, missing recovery, failed object check or uncertain process check blocks an original-removal candidate. Passing content recovery does not prove no external application refers to the old absolute path.

ZIP files require per-input `zip_mode: contents` consent. The outer archive is streamed into shared file objects without retaining a full expanded staging copy. Relative paths, supported file bytes, declared modes/times and empty directories can be reconstructed. Archive bytes, comments, order, signatures, compression settings and filesystem metadata cannot be reconstructed. Declared times use UTC; ZIP entry identity is virtual, not an original inode. ZIP does not supply native extended attributes: do not fabricate an empty attribute set, and do not weaken ordinary-folder attribute verification. Nested archives are stored as files. Unsafe/duplicate/case-conflicting paths, links, encrypted members, unsupported compression and budget violations are rejected.

The report distinguishes candidate file lengths, observed source allocation blocks, added managed files, retained verification copies, and modeled net change. APFS clones/snapshots, directory blocks, final records, concurrency and actual volume-free change limit accuracy. Keeping all readback copies may make net change negative. A separate conditional model may show what changes if the user later chooses to remove those generated copies; no removal is performed or automatically authorized.

Read `folder-import-report ID`, or use `--refresh` to recheck originals, stored content and retained recovery evidence. Rechecking keeps the old report and writes a new receipt. Restored reports must be revalidated and cannot inherit candidate conclusions. There is no general original-folder deletion executor in this workflow.

Exact internal full-snapshot recovery copies can be reused only after fresh byte/metadata readback; a name, neighboring SHA or old success receipt is insufficient. External or partial restores are not borrowed. Invalid copies and failure evidence remain; a new copy is created only when required. First-time per-version restoration still adds full copies. This reduces repeat-review growth, not the initial retained-copy cost, and it does not by itself make net disk usage decrease. Restored preview jobs lose their old capacity clearance and must be analyzed again.

Readback checks file identity around streaming reads and rechecks the entire inventory and root at completion. A change during the scan invalidates reuse. This is observed verification of an editable copy, not a promise of future immutability.

Current bounds: 2–32 inputs, folder scan at most 250,000 entries / 128 GiB each, ZIP at most 100,000 expanded entries / 128 GiB and bounded compression ratio, snapshot manifest at most 32 MiB. File bodies stream in bounded chunks; per-input state is retained on disk rather than keeping every version's manifest in memory. These limits and synthetic tests do not establish large-project throughput. Allow space for the library and retained full readbacks before running; no existing file is automatically removed to make room.
