# Git 版本关系图：功能、语义与实现契约

状态：Reprise 0.8.0 保留的正式 Git 工作台；核对日期：2026-10-26。实现源为 `web/graph-layout.js`、`web/live.js`、`src/reprise/git.py` 与 `src/reprise/workspace.py`。工作目录中的早期 Demo 和语义审查继续保留，但不作为正式实现入口。

这部分的产品目标是让人看清版本如何延续、从哪里分开、哪次提交合入了哪段历史，同时保留选中圆点、连续竖线、圆角绕行和紧凑列表的视觉。换成网页、游戏、文档、CLI 或其他内容的仓库，关系图都使用同一套 Git 对象规则。内容类型影响详情和运行能力，不影响图的身份与连线。

## 1. 先读懂图

| 元素 | 含义 | 实现依据 |
| --- | --- | --- |
| 一个圆点 | 一个确定的提交 | 完整 SHA；不能以短 SHA、标题、文件内容或展示编号去重 |
| 圆点之间的实线 | 真实的子提交 → 父提交关系 | commit 的有序 `parents`，每个父对象一条边 |
| 左侧蓝色参考线 | 选定参考 tip 的第一父链 | 从 `mainTip` 连续沿 `parents[0]` 回溯，固定在第 0 列 |
| 红、绿等侧线 | 当前快照中其他第一父路径及其连接 | 通用布局计算，不使用固定项目的手写轨道 |
| 多条父边的圆点 | 合并提交 | `parents.length > 1`；圆点稍大，与标题是否含“合并”无关 |
| 深色外圈、内圈填色 | 当前选中版本 | 只改变选中状态，不增加提交、不改父关系 |
| 虚线 | 父 SHA 已知，但父提交不在本次加载集合中 | 连接到边界位置；不能伪装成无父根提交 |
| 淡化的关系行 | 搜索/收藏等筛选未命中的真实提交 | 仍保留圆点和完整关系，避免把上下两个命中结果假接起来 |
| 独立历史分隔 | 相邻显示行不属于同一已知连通分量 | 只加说明，不造连接、不更改拓扑 |

屏幕上是**子提交在上、父提交在下**。看发展过程时从下往上读；向下追踪的是祖先。因此合并节点往下可能有两条“分开的线”，仍然是在表达合并。日期用于辅助阅读，时钟错乱时也必须先服从祖先关系。

分支名和标签是指向提交的引用。多个名字指向同一 SHA 时仍只有一个圆点；新建一个仍指向旧提交的分支不会凭空生成新圆点。轨道位置与颜色不能恢复历史分支名称，也不能表达永久的分支归属。[Git 官方：分支引用](https://git-scm.com/book/en/v2/Git-Branching-Branches-in-a-Nutshell)

两条线只在**真实提交圆点**处表示有共同端点。没有圆点的交叉不表示合并；相邻、相同颜色、相似标题和相同文件树都不构成关系。

## 2. 必须保持的十条不变量

1. 一个完整 SHA 对应一个提交节点；SHA-1 的 40 位和 SHA-256 的 64 位均按完整字符串处理。
2. 输出边集合与输入的 `(childSHA, parentSHA, parentIndex)` 集合完全相同：不补线、不丢线、不改线。
3. 合并父序保持原样。第一个父对象与额外父对象的展示职责不同，不能先按时间、标题或 SHA 排序父列表。
4. 所有已加载父对象都在其子提交下方；日期提示不能越过拓扑约束。
5. 参考线必须来自一个明确 tip；普通选中、筛选、收藏、编辑说明、预览和运行不更换它。
6. 线不能穿过无关提交圆点，造成一条不存在的父子关系；需要时动态增加绕行列。
7. 未加载父对象保留原 SHA 和虚线边；不能换成别的仓库中的相似版本，也不能隐去该边。
8. 同一输入图、排序提示和参考 tip 得到确定的行、路径、轨道与边。操作界面状态不会重新分配图。
9. 布局输入不被修改；DOM 尺寸只用于像素坐标，不参与修改 `parents`、SHA 或 ref。
10. 导入和读图不 checkout、reset、commit、fetch、运行 hook/filter 或安装到源仓库。运行、媒体、AI 提案与图数据分开。

这是维护要求，不是任意规模、任意损坏仓库的“永不出错”承诺。规模和数据缺失边界见第 8 节；回归验证见第 9 节。

## 3. 数据从哪里来

```text
源仓库中的 Git 对象与本地 refs
  → Repository.info / refs / history
  → workspace.repository_snapshot / snapshot
  → /api/workspace/snapshot
  → live.js prepareGraph
  → RepriseGraph.layout
  → renderHistory + drawGraph
```

### 3.1 Git 读取层：只提供事实

`src/reprise/git.py` 的 `Repository` 负责定位普通、裸仓库和 linked worktree，读取 HEAD、当前分支、对象格式及浅历史状态。空仓库可以没有 HEAD；detached HEAD 可以有提交但没有分支名。

`refs()` 读取本地完整 ref 名、目标 SHA、类型和原始对象 SHA。annotated tag 会解析到最终目标；指向 tree/blob 的标签仍可作为引用清单记录，但不能当成提交 tip。

`history()` 对已解析的 tip 使用 `git log --topo-order`，读取完整提交 SHA、父列表、主题、作者与时间。浅克隆中 Git 遍历会把边界当成停止点；实现额外读取原始 commit header 中的父对象，保留“还有父 SHA，但对象未加载”的事实。不能改成只读 `--first-parent`，否则会丢掉支线和额外合并父边。[Git 官方：提交排序及 first-parent](https://git-scm.com/docs/git-log)

Git 调用禁用 replacement 对象、隐式 lazy fetch 和可选锁，并隔离继承的 Git 环境/全局配置。状态读取采用托管的私有元数据视图，保持源暂存区不变。工作区未提交文件只出现在状态/详情中，不成为图节点。

### 3.2 快照层：固定可达起点，再去重

`src/reprise/workspace.py` 的 `repository_snapshot()`：

1. 读取项目 HEAD 与本地 refs，将指向 commit 的不同完整 tip 去重，HEAD 优先。
2. 每个 tip 固定为已解析的 SHA，通过 `history_tips()` 一次最多读取 2000 条。已加载且祖先完整、数量未超限的 tip 复用已读结果；有边界或超过数量仍由 Git 遍历。HTTP `history()` 继续支持每页最多 200 条的分页读取。不能重新解析移动中的分支名，造成重复或跳项。
3. 按完整提交 SHA 合并各 tip 的可达提交；同一个提交经多个分支读取也只有一份。
4. 装饰当前 ref 名、绑定该 SHA 的人工说明、读取来源 `source_project_id`。
5. 以提交时间和 SHA 排序，作为前端的次级顺序提示；最后显示顺序仍由布局的拓扑排序决定。
6. 输出 refs、状态、warnings 和显示集合的指纹，说明、ref 名称与存档 catalog 变化也更新指纹。它不是全部 Git 内容的校验和，也不是原子锁。

快照跨多个只读调用完成。若源仓库同时被其他程序更新，这些调用不是整个仓库的原子事务；已捕获的 tip 在本次分页中保持固定。刷新可以读取新的快照，不能将前后两个快照的 ref 名称当成永久身份。

`snapshot()` 只合并用户显式关联的历史存档，验证共同提交，完整 SHA 去重，当前仓库记录优先；存档新增版本保留真实来源。可选 catalog 只限制存档显示范围。父列表仍保留原值，catalog 排除的父版本会成为边界，不能将子提交改接到更早的可见节点。存档同名 ref 不覆盖当前仓库 ref；也不会生成跨仓库猜测连线。

## 4. 参考线怎样选

当前 `live.js::prepareGraph()` 的实际优先级：

1. 已保存的 `prefs.main === 'HEAD'`：明确使用该项目 HEAD。
2. 已保存的完整 ref 名存在且指向 commit：使用它的已解析 SHA。
3. 否则使用存在且指向 commit 的 `refs/heads/main`。
4. 否则使用项目当前分支对应的 `refs/heads/<branch>`。
5. 否则回退到项目 HEAD；空仓库为 `null`。

`prefs.main` 是按项目存储的浏览器偏好；当前普通界面没有公开的参考线选择控件。主线选择与浏览器当前选中 SHA 是两个状态。没有 `main` 的 `trunk`、`master`、中文分支仍可以显示，不能给这些仓库伪造 `main`。

这是 Reprise 的展示策略。当前实现**不自动推断远端默认分支**，也不自动 fetch。detached HEAD 若仍有本地 main，默认参考线仍可选 main；显式选择 HEAD 才沿 detached tip。参考线不一定等于团队业务上称为主线的分支。

布局模块本身更严格：只接受调用者提供的 `mainTip` 或唯一匹配的 `mainRef`。不提供时无特殊主线；未知 tip 生成 `UNKNOWN_MAIN_TIP` 诊断，不替换成数组第一项。

## 5. 通用布局怎么实现

### 5.1 输入、输出与失败

浏览器调用 `RepriseGraph.layout(commits, options)`；Node 使用同一文件的 CommonJS 导出。模块无 DOM、无项目路径、无内容类型判断、无网络、无第三方依赖。

```js
const graph = RepriseGraph.layout([
  {id: 'M', parents: ['A', 'B'], order: 3},
  {id: 'B', parents: ['R'], order: 2},
  {id: 'A', parents: ['R'], order: 1},
  {id: 'R', parents: [], order: 0}
], {mainTip: 'M', refs: [{name: 'refs/heads/trunk', tip: 'M'}]});
// 参考链 M → A → R；另外保留 M → B 与 B → R。
// 例子使用符号 ID；真实工作台必须传完整 SHA。
```

输入：`id` 为非空字符串，`parents` 为有序字符串数组，`order` 可选且必须是有限数字。模块复制父数组，不修改输入。非法节点、重复 ID、重复父对象、非法顺序和环分别抛出带 `code` 的 `GraphLayoutError`；不能捕获后悄悄删边继续画“看起来正常”的图。

| 输出 | 用途 |
| --- | --- |
| `rows` | 每个节点的 row、lane、routeId、parents、children、refs、isMain、isMerge |
| `mainTip / mainPath / mainBoundary` | 参考 tip、已加载第一父链及其未加载终点 |
| `routes` | 排版路径及其占用区间；不是 Git 分支对象 |
| `edges` | 全部真实父边，父序、类型、绕行 rail、逻辑点列与缺失标记 |
| `boundaries` | 不在输入集合中的父 SHA、共用该父对象的子节点及边界位置 |
| `laneCount / rowCount` | 包含节点、绕行列及缺失边界的实际尺寸 |
| `diagnostics / semantics` | 缺失父对象、图外 ref、未知参考 tip 等事实与语义说明 |

### 5.2 先做拓扑排序

建立每个提交的子节点列表和未处理子节点计数。没有未处理子节点的提交进入 ready 集合，自上而下弹出；处理一个子提交后减少其父节点计数，父节点全部子节点已处理后才允许入队。这是反向 Kahn 拓扑排序。

ready 节点之间优先使用较大的 `order`；没有提示时使用自然降序 ID，避免结果依赖输入数组偶然排列。拓扑优先级始终高于 `order`。处理数量少于输入数量说明存在环，必须明确报错。真实 commit 的祖先 DAG 不应该有环。

`live.js` 根据快照时间排序赋予 `order`。因此固定提示时任意打乱输入数组，图仍一致；若改变提示或增加提交，则允许重新布局。

### 5.3 分解第一父路径

先从明确参考 tip 沿第一个父对象建立 `mainPath`。遇到真正无父提交停止；遇到未加载父 SHA 记为 `mainBoundary`。

然后依次处理尚未分配路径的拓扑节点，沿第一父链走到根、未加载父对象或已属于另一条路径的节点。主路径 ID 为 `main`，其他路径 ID 为 `route:<headID>`。一个节点只归属一条**排版路径**，但可以被多个 refs 指向，并被多个后继提交引用。

### 5.4 按路径生命周期分配列

每条路径占用闭区间 `[startRow, endRow]`；终点包括它接到的已知父节点或缺失边界行。主路径在第 0 列预留整个图的高度。其他路径按起点行及路径 ID 排序，从最左可用侧列开始放置。

区间重叠或接触的两条路径不能占同列。已经结束、与后来路径没有区间重叠的列可以复用。因此上下两段都在 x=1 并不代表同一个分支。没有显式主线时普通路径可从第 0 列开始。

### 5.5 每个父对象分别连线，必要时绕行

先安排所有第一父边，再安排额外合并父边，优先保护连续参考路径。第一父边优先沿子节点所在列；额外父边优先沿父节点所在列。

对候选竖列检查：

- 子/父行之间是否存在无关圆点；
- 该列是否已经有与本边竖段重叠的连接。

冲突时从两端列右侧寻找空列，动态增加列，不能退回有冲突的列。每条边生成正交逻辑引导点，离开子行 `0.28`、进入父行前 `0.28` 处横向转弯。最后按子行和 `parentIndex` 输出，保留父序。

缺失父对象按 SHA 生成一个共用边界，不按子节点复制假提交。所有边界在最终节点之后的边界行；尽量沿其第一父路径所在列，冲突时使用其他列。`kind=boundary` 与 `missingParent=true` 决定虚线表现。

### 5.6 必须保护的“合入后继续开发”案例

```text
R  无父对象
A  parents=[R]       支线当时提交
B  parents=[A]       支线后来继续开发，尚未合入
M  parents=[R, A]    主线只合入 A
```

参考 tip 为 M 时，主路径是 `M → R`，支路为 `B → A → R`；额外合并边是 `M → A`。边 `M → A` 必须绕过 B 的圆点。**绝不能画成 `M → B → A`，也不能为了闭环改成 `M → B`。** 这个案例已成为正式回归测试，不依赖示例项目的版本编号。

## 6. 颜色、圆角与实际行高

布局返回的 `colorIndex` 是路径序号。实际 `live.js` 另按闭区间分配显示颜色槽：参考路径蓝色；侧路径使用红、绿、紫、棕，并按当前五色 palette 循环。生命周期不重叠的侧路径可以复用颜色；并行路径多于 palette 时颜色也会重复。身份判断必须依靠真实节点/边，不能仅凭颜色。

`drawGraph()` 把逻辑坐标投影到 SVG：

- x 为 `19 + lane * 18` CSS px；包含绕行列动态计算 SVG 与文字 gutter 宽度，最小图宽 76px。
- y 读取每个真实 DOM 行的 `offsetTop`，加上该行标签的中心。详细视图对齐 meta，32px 紧凑视图对齐标题。
- 小数逻辑行在上下节点实际 y 之间插值；独立历史说明、标题换行和摘要长度都包含在实际布局中。
- `rounded()` 去除连续共线引导点，用最大 7px、且不超过两邻段一半的圆角半径产生二次贝塞尔曲线；只美化转角，不改端点。
- 路径 2px；普通圆点半径 3.8px，合并圆点 4.6px；选中外圈半径 8px。缺失边界边使用 `3 3` 虚线。

密度切换、筛选、语言与说明变化、窗口 resize 后必须重画像素坐标。需要扩大 gutter 时，应先应用宽度让文字重新排版，**再**量测行高；否则复杂分支图的圆点会与正文错位。不能写死 80px 行距、三条轨道或固定节点 y。

## 7. 交互可以改变什么

| 操作 | 可以改变 | 必须保持 |
| --- | --- | --- |
| 选中版本 | 详情、外圈、当前 SHA、滚动位置 | 参考 tip、所有节点和父边、路径颜色 |
| 搜索 / 收藏定位 / 引用筛选 | 命中重点、上下文行的高度与淡化、匹配详情 | 全部关系节点和父边；零匹配也保留图 |
| 点击关系行 | 返回该提交上下文，必要时解除妨碍选择的筛选 | 原始身份与祖先关系 |
| 画面 / 版本关系 | 缩略图或固定紧凑的关系图、选中定位 | 同一版本身份；关系图的所有节点、父边、轨道与颜色 |
| 语言 / 人工标题摘要 | 展示内容、文本尺寸 | 完整 SHA、parents、refs；不按新标题重排 |
| 预览 / 运行 / AI 提案 | 详情与独立任务状态 | 不产生提交、不改变源仓库和图 |
| 刷新 Git | 新快照、ref 位置、新增/减少的可达对象 | 重新按真实快照生成，不沿用失效的父关系 |

筛选使用 `match()` 判定重点，`renderHistory()` 仍遍历 `state.commits` 全集。`independentHistoryStarts()` 按真实父关系求连通分量，包括共用的未加载父 SHA；仅在相邻行分量变化时插入分隔。多个独立历史可能在拓扑顺序中交错，分隔不意味着本次已读到它们的全部历史。

请求有项目/选中请求序号及详情中止控制，迟到响应不能覆盖后来选中的详情。`repriseWorkspace.graph()` 暴露只用于观察的布局快照，正式浏览器测试可比较筛选前后完整 DAG；不要通过这一调试入口编辑源 Git。

「画面」和「版本关系」共享同一批版本身份。图片列表不重建 Git 关系；切换两种视图保留当前所选版本，并将已显示列表中的所选项滚入视野。Git 项目默认关系图，文件夹留稿默认画面列表；文件夹的保存顺序不表示源仓库的分支历史。缺少图片时保留明确空状态。

## 8. 换仓库时怎样避免误画

| 情况 | 正确行为 |
| --- | --- |
| 线性历史 | 连续父链，不添加支路 |
| ref 改名、删除或多个名字指向同一提交 | 名称装饰变化；仍可达的同一 SHA 与其父边不变 |
| 多个后续提交源于同一父提交 | 各自保留真实父边，动态侧列 |
| 2/3/N 父合并 | 每个父对象一条边，第一父路径保持独立职责 |
| fast-forward | ref 前进，不凭空新增合并节点 |
| squash / cherry-pick / rebase 后的新提交 | 按新 SHA 和真实父链画；内容来源不能冒充祖先边 |
| 标题叫“Merge”但只有一个父对象 | 普通提交，不能按标题识别合并 |
| 相同标题、相同 tree、相同日期 | 仍按完整 SHA 区分 |
| 独立根、orphan 历史 | 分隔且保留真实节点，不补共同根 |
| 空仓库 | 空图，不生成 HEAD 圆点 |
| 裸仓库、linked worktree、detached HEAD | 用相同 Git 对象读取，不依赖 `.git` 必须是目录或存在工作区 |
| 浅克隆、读取上限、catalog 排除父版本 | 已知父 SHA 保留虚线，不假装历史起点 |
| 不同内容类型 | 图完全复用，详情/运行能力单独处理 |

普通合并和 fast-forward/squash 的父关系不同；能否画合并只看实际 commit 数据。[Git 官方：merge 行为](https://git-scm.com/docs/git-merge) commit 对象可以有零个、一个或多个父对象，不同 tree 内容不是分支判据。[Git 官方：commit-tree](https://git-scm.com/docs/git-commit-tree)

当前明确边界：

- 每个来源最多读 64 个不同 commit tip，每个 tip 最多 2000 条。命中上限会输出 warning；这不等于仓库只有这些历史。
- 只读本地已知 refs 可达历史及 HEAD；不包含未被引用且不可从这些 tip 到达的 dangling/reflog-only 提交，也不自动联网获取历史。
- 目前边界模型统一表示“父提交未在加载集合中”。虚线不能区分分页上限、浅克隆、对象缺失或 catalog 过滤；原因需结合仓库状态与 warnings。没有点击虚线继续加载的功能。
- 同一快照内颜色/列稳定；增加历史、更换参考 tip 或刷新 refs 后可重新布局。不承诺跨快照永久配色或最小宽度。
- 轨道数动态增加。关系图固定使用 32px 紧凑行，移除了详细/紧凑选项。宽图为标题保留至少 180px 可读空间；桌面侧栏按需加宽到最多半屏，超过可用宽度时横向滚动，手机显示提示。不会删边或合并冲突轨道来省空间。
- 当前仍渲染全部已加载节点，没有大图虚拟化。新增真实 Git 压力仓库验证 1301 个提交、1620 条父边、16 条并行分支和 320 个合并节点；逐项核对身份、父序、避碰、全深度圆点对齐、搜索与跨视图定位。这个规模通过不表示无限历史均已验证。
- 布局的 ready 排序和避碰遍历不是面向无限规模的索引算法。若扩大加载上限，必须先做真实规模性能/布局验收，不能只提高数值。
- 损坏的对象/非法图明确失败；没有自动修复源仓库。重复父对象被布局作为非法输入拒绝，不宣称支持任意手工构造的异常 commit。

纯布局测试不需要浏览器、不需要安装 npm 依赖，但测试 runner 需要 Node 18+：

```sh
npm run test:graph
# 或使用已准备的 Node：
/path/to/node --test tests/graph-layout.test.cjs
```

Python 标准测试会自动运行图契约和真实 Git 集成测试；使用 `PATH` 中的 Node 或 `REPRISE_NODE`。没有 Node 时这些 JS 相关测试明确跳过，Python/Git 基础运行仍不依赖 Node。发布图相关修改时不能把跳过当成已验证：

```sh
REPRISE_NODE=/path/to/node PYTHONPATH=src python3 -m unittest discover -s tests -v
REPRISE_BROWSER_TESTS=1 REPRISE_NODE=/path/to/node \
  REPRISE_PLAYWRIGHT=/path/to/playwright/index.mjs \
  REPRISE_BROWSER=/path/to/chrome \
  PYTHONPATH=src python3 -m unittest discover -s tests -v
```

修改图相关代码时：先确定变化属于数据、布局还是渲染；为新 Git 模式或已复现缺陷补真实语义断言；修改正式源而非 Demo；运行受影响测试和项目完整测试。几何修改另外验证真实浏览器的圆点、父边与文字对齐。测试仓库、JSON 快照、截图和失败诊断全部留在 `work/test-artifacts/`。

新前端、换框架或重做侧栏仍须通过同一组图契约。可以替换排版策略和圆角实现，但不得靠手工 lane、固定版本编号、标题相似度、内容相似度或 AI 输出决定父关系。
