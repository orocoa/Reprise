# Reprise 产品方向：留一稿，凭画面找回

本文件记录 Reprise 0.8.0 的产品方向。版本图片与真实 Git 关系图均为保留的主要浏览能力；实际交付与维护范围以 [功能清单](FEATURES.md) 为准。

## 为谁做，解决什么

主要用户是用 AI agent 或编辑器反复修改本地网页、需要凭画面找旧稿的人。首先服务正在与 agent 协作的人，不要求理解 Git、提交对象、构建配方或命令行；不扩展成面向所有电脑用户的文件管理器。

使用情境是：**“调了几版，想找回之前那一版。”** 必须先主动保存：修改前留 A → 改成 B 再存 → 凭图认出 A → 取到新文件夹继续改。Reprise 不会持续自动保存，无法事后找回从未保存过的内容。每稿有名称、时间和可用时的对应画面；需要时比较并取回选定文件。

它不是线上 URL 收藏夹，不靠抓取别人网站建立收藏，也不把版本画面当作任何时刻都能重新运行的保证。

项目目标是把自己的有用工具做得更清楚、更方便，在 GitHub 分享并做小规模传播。Stars、收藏和交流可以是分享成果；它们与实际成功使用、后续复用是不同信息。无需以企业采购、付费转化或公司规模来证明这个项目值得存在。

## 主要入口：Skill，认稿用工作台

用户已经在与 agent 做网页。目标体验是选择 Reprise Skill 后说“打开”，只展示工作台，不导入或保存当前目录；要留稿时再说“保存当前网页这一稿”，沿用当前已明确的项目。中文“倒带”与英文 Reprise 指同一产品，当前 Skill 标识是 `reprise`；显示名不是通用 `@` 别名的实现证据。各客户端发现与选择方式以[接入说明](AGENT-SKILL.md)为准，本候选原生触发仍需实测。

Skill 复用固定本地核心，按对话语言传 `--lang zh|en`。文件保存和画面完成是两个结果；配置缺失或截图失败需要如实报告。画面比较在可视工作台完成，不在工具里再接一套 AI 对话与模型设置。

主要交付是轻量源码 Skill + 脚本，包含固定核心源码与可视工作台。agent 首次检查并复用宿主已有 Python/Git；自动截图另查 Node、Node 版 Playwright 与浏览器。缺少时按成熟官方方法，在已有任务授权和宿主正常许可下安装到 Reprise 专用位置，不写入受管网页源仓库。不让普通用户手填环境变量，不把依赖恰好存在说成没有依赖，也不承诺每个 agent 都能完成安装。

开发者列清基础环境即可：Python 3.9+ 与 Git；截图需要 Node/Playwright/匹配浏览器。3.9 是代码下限，新装选择仍维护的版本；当前 Playwright 1.62.1 要求 Node 20+，新装优先受支持的 LTS。核心不需 pip 第三方包。

本次交付只保留源码 Skill 和双语内容包。独立 App 壳不作为主入口。各客户端原生接入、宿主依赖复用、缺依赖安装和外部用户独立完成分别验证。

第一成功标准是：明确本地项目 → 保存 A 的文件和画面 → 修改并保存 B → 在中/英文工作台凭图辨认 A → 取出到新目录继续改。现阶段静态 HTML 已具备快捷采集路径；标准独立 npm/Vite 项目已有经 React 验证的待批准安装/运行计划，先保留稿件、明确批准后再出图；Next、其他包管理器和自定义脚本仍需明确运行配置。不能用静态网页通过掩盖目标人群常见框架的缺口；优先补主线中实际遇到的阻塞，再考虑扩展功能。

## 本轮体验收口与冻结

以 Agent 完成安装为主入口，直接命令供熟悉环境的人按需查看。用户可明确说“本轮修改前后都帮我留稿并带画面”，由当前 Agent 在这两个节点保存；不新增后台常驻、监听器或跨聊天触发器。

首次保存说明范围，名称可留空。已明确保存截图偏好的项目，后续点击保存或快捷键即可留稿；需要名称时保留命名入口。首次按项目问清是否保存画面并持久化答案；确认实际配置后持续沿用，失败不重置选择。单次截图成功本身不替代用户的项目级选择。整稿恢复后提供可复制给 Agent 的新目录继续指令，部分文件恢复不冒充完整网页。

通用功能扩展冻结。已有高级能力和文件继续保留、按需访问；后续只处理主流程实际阻塞及必要的完整性、兼容性问题。不得把本轮简化扩成云同步、通用清理、新框架适配或另一套 AI 产品。

## 从用户任务重新分层

### 第一层：留下一稿，再认出它

1. 沿用对话中已明确的本地网页项目；项目不明确时再选择文件夹。
2. 给当前内容保存一稿；名称可以很普通，例如“更自然的过渡”或“收紧间距之前”。
3. 是否采集画面按本次明确请求和项目既有偏好处理；工作台保存对话框以实际选择为准，普通 Skill 保存不会自动要求截图。采集前说明本机网络与独立副本范围。需要选择入口或配置时，文件先保存，画面另行完成，不要求静态单入口网页用户编辑 JSON。
4. 默认浏览视觉历史画廊：画面、版本名称、保存时间是主要信息。没有画面时明确显示尚未保存画面，仍能查看文件和取回内容。

保存文件内容与截图是独立结果。画面未完成，不撤销已经保存的一稿，也不显示“画面已保存”。普通非网页文件夹默认只保存内容，不要求选择截图策略。

如果同一版本有多个独立网页入口，让用户按名称或路径选择要保存画面的网页。不要静默打开某个示例目录，把它当作整个项目。

### 第二层：比较并取回

用户先选择两稿，比较各自保存的画面，再按需要展开文件变化。文件变化始终来自选定的两个版本；没有画面时仍可完成文件任务。

取回操作明确说明来自哪一稿、涉及哪些文件和保存到哪里。默认输出到原项目同级的新目录，位于 Reprise 数据目录之外，保留当前项目；完整稿件可重新加入，继续修改和留稿。原项目上级目录不存在或不可写时，说明失败并展开手填位置，不回退到数据目录。成功后能打开结果位置。关闭比较、文件详情或恢复结果后回到原来的版本与选择。

“取回旧文件”不自动保证它与当前工程的其他文件兼容。工具需要准确完成所选范围，不擅自把它覆盖回工作目录。

### 第三层：有需要再管理

已有 Git 历史、详细代码差异、运行配置、手工截图、备份迁移、旧副本导入、去重和存储管理继续保留。把它们放在对应任务或高级管理中，避免第一次使用就像在配置一套存储系统。

整理旧文件夹是可选任务。既有版本管理和数据校验不能因为界面简化而消失；它们也不需要成为新用户必须先理解的功能清单。

## 静态网页的一次明确操作

用户在已说明截图范围的对话框点“保存这一稿”，或单独点“保存配置并截图”，是本次明确操作的起点。应用读取该版本的文件，找出静态网页入口，生成固定且受限的配方，保存到该完整版本标识，再调用现有采集服务。

- 配方只能是 `static-web`，没有安装、构建或启动项目命令，浏览器使用本地网络范围。
- 检测、浏览画廊或读取预览状态不会执行项目，也不会产生批准记录。
- 需要构建的源码不会被静默转成 `command-web`；此时给出简短的设置或手工提供画面入口。
- 已知缺失素材、远程素材和不明确的多个入口需要说明或选择，不伪装成完整画面已经就绪。
- 每次目标都是选中的确切版本；默认不继承另一版的执行批准；只有用户另行明确开启固定配置的未来复用时才沿用。任何情况下都不用另一版画面填补空白。
- 已保存的手工截图继续标明由提供者指定版本归属，不冒充自动采集结果。

“入口可准备”只说明没有发现阻塞静态入口的已知条件。JavaScript 的动态请求、交互状态、浏览器依赖和最终画面仍由采集结果判断。工具保留真实诊断，不因为预检通过而宣称截图成功。

## 安全保持不变，技术解释按需出现

源文件夹和导入 Git 仓库保持原样；保存内容、准备预览、运行、采集、恢复与删除仍是有明确范围的动作。恢复校验、确切版本身份和原始 Git 关系保留。

普通界面用“这一稿”“保存画面”“比较”“取回”描述任务。完整 SHA、配方 JSON、内容散列、字节统计和全部日志放在详情中。技术事实需要准确，但用户不应为了完成基础任务先学会它们。

本地快照不等于独立备份。使用 AI agent 时遵循相应数据边界；产品不以“本地”暗示内容绝不会进入用户主动调用的 agent 上下文。

## 与现有内容的衔接

面向个人网站和作品集创作者的演示，先出现可见效果，再解释具体操作。与“再自然一点，到底怎么跟 AI 说”这类内容形成连续任务：调参数、看对照、带走说明或代码，然后用 Reprise 记住尝试过的版本。

一句合适的传播表达是：**“调了几版，还是想要之前那一版。”** 演示只需展示一次真实的保存、辨认和取回，不需要突然介绍整个存储管理系统。

使用合成项目或已经明确允许展示的材料，避免露出个人信息、私人路径和真实敏感文件。文案自然、具体、少术语；小红书正文不放外链。公开演示标明对应版本，不把本地候选能力写成已公开发行能力。

可以记录 GitHub Stars 和内容反馈作为分享信号；另外记录用户是否独立完成了真实任务。两类成果都可以有价值，但不要互相替代。

## 本阶段验收问题

- 第一次使用的人能否知道这是自己的本地网页项目，而非线上网址收藏？
- 能否在不编辑 JSON 的情况下，为可直接运行的静态网页保存确切版本的画面？
- 多入口、依赖缺失、远程素材或截图失败时，能否知道下一步怎么做，同时保留已存文件？
- 在画廊里能否认出想找的一稿，并且只比较或取回自己选择的内容？
- 纯文件资料能否直接保存和取回，不被截图设置打断？
- Git、备份和整理等既有能力是否仍能找到，同时不占据基本任务的第一层？

这些问题验证实际体验，不设置商业化门槛，也不把测试样本成功描述为真实用户复用。

<details>
<summary>实现参考：静态准备 helper 契约</summary>

`prepare_quick_preview(repository, sha, *, root=None)` 位于 `src/reprise/quick_preview.py`。输入必须是完整的 40 位或 64 位 SHA；可选 `root` 只能选择该版本检测到的独立静态网页入口。

| 返回字段 | 含义 |
| --- | --- |
| `sha` | 输入并再次解析核对过的完整版本标识 |
| `status` | `ready`、`choose-entry` 或 `needs-configuration` |
| `recipe` | 只有 `ready` 时存在；已经过 `validate_recipe` 规范化 |
| `root` / `entry` | 当前选定的站点根目录与入口文件 |
| `candidates` | 各独立入口、是否可准备以及已知阻塞原因 |
| `warnings` | 确切版本检测产生的诊断 |
| `requires_save` | 始终为 true；helper 本身不保存、不执行 |

应用层在用户明确操作后保存该 `sha` 的配方，再调用采集。调用者不能把 `ready` 当作运行批准、采集成功或可复用其他版本画面的理由。

</details>
